## Why this use case fits WebMCP

A 38-minute podcast contains maybe five lines that, in the right order, are a story. Finding them is a search problem with **no correct answer — only taste** — and you cannot judge a candidate without *hearing* it.

The sponsor demos are transactional: a storefront, a reservation, a return. There the agent *completes* a task you'd rather not do. Cutting a short isn't that shape. There is no answer to find, only a judgement to make, and the person has to hear the result to make it. So the work splits along one axis:

- **The agent does:** read 547 lines in a second · hear where the voice lifts across 38 minutes · trim to word boundaries · cut on breath.
- **The human does:** decide which five lines are a story · decide whether that's the right kind of energy · say "too long" after hearing it.

Neither half works alone. That is why this is a WebMCP app and not a chatbot with an API: **the tools have to live where the person is listening.**

## How it creates a better user experience

Cutroom registers **33 tools** on `document.modelContext`. Three things make it more than a wrapper:

**1. The agent can hear.** `findEnergyMoments` reads the RMS envelope of the actual audio and returns where the speaker's voice lifts above their own baseline. On the demo episode the strongest moment is *"I mean, isn't that amazing that we did that?"* at 29:38 — lift ×2.85 — a line no keyword search ranks, because the signal is in the delivery. Five of the 33 tools read the audio rather than the transcript; it runs in 1.7 ms over 21,000 samples.

**2. Taste travels both ways.** Agent proposals land as *pending* clips — dashed, each with a one-line reason — never as silent overwrites. A thumbs-down or a steer chip ("Tighter", "Colder open") comes back through `getReelState` as `humanVote`, `humanNote`, `humanAsked`. The agent revises to the person's taste, not its own. Every call appears in a visible ledger, and everything is undoable.

**3. It knows the craft.** `checkFlow` reports what an editor would flag: a hook opening mid-thought, a join landing on speech instead of in a pause, a sentence sheared off. `cleanUpCut` removes stammers and dead air from the *middle* of a clip and closes the audio up behind them. `getCutManifest` hands over every span to a hundredth of a second plus an ffmpeg command — which has been run and verified: 30.53 s out for a manifest claiming 30.5 s. `renderVideo` produces a 1080×1920 H.264 MP4 with word-by-word captions, in the browser, with no server.

## What people and agents can accomplish together that wasn't possible before

Before: you scrub 547 lines by hand holding a story in your head, or you hand it to an AI that returns one cut you can't hear, feel is wrong, and have no vocabulary to correct. Either way you end up doing it by hand.

Now: the agent proposes two or three *contrasting angles* from across the whole hour; you hear each in seconds; you thumbs-down a line and the agent knows exactly which line and revises around it; it checks its own cut like an editor; it hands back timestamps that survive contact with a real pipeline. **The agent makes your judgement cheap.** That loop — propose, hear, react, revise — did not exist, because the agent had no ears and no way to read the person's reaction.

It also works the other direction: `loadTranscript` lets an agent bring *its own* material in, so an agent that already holds a transcript can hand it over and start cutting.

## How WebMCP is implemented

- **Registration:** 33 tools via `document.modelContext.registerTool()`, each with a JSON-schema `inputSchema`, `annotations.readOnlyHint`, and `additionalProperties: false`. Registered in `<head>` before first paint, so a runtime that snapshots page tools early finds them. `navigator.modelContext` is a true fallback only (reading it logs a deprecation).
- **Environment:** origin isolation (`Origin-Agent-Cluster: ?1`), `Permissions-Policy: tools=(self)`, `/.well-known/mcp.json` generated from the registration code so it cannot drift, and `/llms.txt` guidance — including what an agent with **no** tool bridge should do (fetch the transcript and waveform, return real timestamps, say plainly it couldn't call the tools).
- **Discovery:** `listCapabilities` returns what's here, the order worth doing it in, and which tools read the audio. `getWorkflowState` reports the stage (empty → drafted → listened → polishing → ready) and what's sensible next.
- **Verification:** `bin/verify.sh` drives the tools over CDP in Chrome 149+ and proves registration, execution, DOM effect and `getReelState` round-trip. A 39-call sweep with deliberately bad arguments (index 99, phrases nobody said, out-of-range times): **0 thrown** — every tool answers with something an agent can act on.
- **Honest limits:** verified end-to-end in **Chrome 149+ with `--enable-features=WebMCP`**. Every documented requirement for ChatGPT's browser is met; on GPT-5.6 Terra with site tools enabled it still reported the bridge unavailable to it, so the Chrome path is the one demonstrated. A judge with no WebMCP browser gets a scripted demo of the *real* tool calls, plus a text-only fallback that is deliberately labelled as worse than the agent.

## Built with

Vanilla JavaScript, no build step, no backend, no API keys. GSAP for motion. whisper.cpp with a verbatim prompt for the transcript (the default run silently strips every "um"; the prompted run keeps 220 of them — which is exactly what the cleanup tools exist to remove). Demo material is NASA's *Houston We Have a Podcast* ep. 327, public domain. Deployed static on Vercel.

## Try it

**Live:** https://cutroom-webmcp.vercel.app — open in Chrome 149+ with `chrome://flags/#enable-webmcp-testing`, or ChatGPT's browser. The pill reads **"33 tools live"** on success. Click **"What is this?"** for the scripted demo; add `?present` to the URL to step through it manually.
